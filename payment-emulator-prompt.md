# Промт для Claude Code — Payment Emulator (упрощённая версия)

## Контекст

Я работаю в платёжной организации. Нужен эмулятор платёжного провайдера (PSP mock)
для тестирования агентов, которые в проде общаются с реальными платёжными
поставщиками через наш внутренний протокол. Сейчас агентам не на чем тренироваться —
только боевые системы. Нужен безопасный тестовый двойник.

Это НЕ платёжная система — деньги нигде не двигаются. Это HTTP API, которое
детерминированно возвращает разные сценарии в зависимости от переданных тестовых
реквизитов, плюс простая веб-админка для просмотра истории без захода на сервер.

Это тренировочный проект для практики работы с Claude Code — сознательно выбран
максимально простой стек, без лишней инфраструктуры.

## Технологический стек

- **Всё в одном процессе**: FastAPI (Python 3.12+)
- **БД**: SQLite через SQLAlchemy (async), один файл `emulator.db`, без Docker
- **Админка**: серверный рендеринг через Jinja2 + немного HTMX для live-обновлений
  статуса без полной перезагрузки страницы (без отдельного фронтенд-билда, без npm)
- **Auth админки**: сессионные куки + один seed-админ, без JWT (избыточно для локального инструмента)
- **Auth агентского API** (`/check`, `/pay`, `/status`): HTTP Basic Auth, один сервисный логин/пароль
  из конфига — просто и достаточно для локального тестового инструмента
- **Фоновые переходы статусов**: asyncio-задача, запущенная в lifespan-хуке FastAPI,
  задержки читает из БД (см. раздел "Настройка задержек через веб" ниже)

## Бизнес-логика: эндпоинты (для агентов)

### `POST /check`
Принимает реквизиты (номер карты/счёта + сумма). Валидирует и возвращает,
можно ли проводить платёж по этим реквизитам, без создания платежа.

### `POST /pay`
Инициирует платёж. Обязателен заголовок `Idempotency-Key` — повторный вызов
с тем же ключом должен возвращать тот же результат, не создавая новый платёж.
Возвращает `payment_id` и начальный статус.

### `GET /status/{payment_id}`
Возвращает текущий статус платежа.

## Сценарии по тестовым реквизитам

Поведение платежа определяется последними 4 цифрами реквизита. Реализуй как
таблицу/dict сценариев в `scenarios.py`, не хардкодь в роутах:

| Суффикс реквизита | Сценарий |
|---|---|
| `0001` | Успех сразу (`success`) |
| `0002` | Отказ сразу (`failed`, decline) |
| `0003` | `pending` → `success` через настраиваемую задержку |
| `0004` | `pending` → `failed` через настраиваемую задержку |
| `0005` | `pending` → зависает в `unknown` (эмуляция таймаута провайдера) |
| любой другой | по умолчанию `success` сразу |

Задержки не хардкодятся и не задаются через переменные окружения — их можно менять
на лету через веб-админку без перезапуска приложения (см. ниже).

## Хранение состояния

- Таблица `payments`: id, requisite, amount, status, idempotency_key,
  created_at, updated_at (реквизит хранится как есть — это тестовый эмулятор,
  реальных номеров карт тут нет)
- Таблица `payment_status_history`: payment_id, status, timestamp, note — полная
  история переходов, это и есть "лог", который показывает админка
- Фоновая asyncio-задача опрашивает платежи в статусе `pending` и переводит их
  по истечении сконфигурированной задержки
- Таблица `scenario_settings`: суффикс реквизита, задержка в секундах, описание —
  начальные значения из таблицы сценариев выше, редактируются через админку

## Веб-админка (Jinja2 + HTMX, без отдельного фронтенда)

- `/admin/login` — простая форма логина, сессионная кука
- `/admin/payments` — таблица платежей: фильтр по статусу, поиск по id/реквизиту
- `/admin/payments/{id}` — детальная страница: текущий статус + таймлайн истории
  из `payment_status_history`. Если платёж не в финальном статусе — HTMX
  poll (`hx-get` с интервалом) обновляет блок статуса без перезагрузки страницы
- `/admin/settings` — страница настройки задержек по каждому сценарию (форма,
  сохранение в `scenario_settings`, фоновая задача читает актуальные значения
  из БД на каждой итерации, без перезапуска приложения)
- Роуты `/check`, `/pay`, `/status` защищены HTTP Basic Auth (для агентов),
  роуты `/admin/*` защищены сессионной авторизацией (для человека в браузере) —
  это два разных механизма, не путать

## Как работать

1. Сначала предложи план в 3-4 фазы (например: модели и сценарии → API-эндпоинты →
   фоновая задача → админка с auth) и коротко опиши, что войдёт в каждую фазу.
   Не пиши код, пока я не подтвержу план.
2. После каждой фазы: покажи, что приложение реально запускается
   (`uvicorn app.main:app --reload`), прежде чем переходить к следующей.
3. В конце создай `CLAUDE.md` с описанием архитектуры, таблицы сценариев
   и команды для локального запуска.
4. Не создавай реальных платёжных интеграций и не подключай ничего к боевым
   системам — это изолированный локальный эмулятор.
